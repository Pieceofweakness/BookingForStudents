# Использование ИИ-ассистентов и анализ рисков

## Генерация тестов с помощью ИИ

**Промпт:**
> «У меня есть таблица `waitlist` в PostgreSQL, предназначенная для листа ожидания. В ней есть поля: `id`, `slot_id`, `student_id`, `position`, `status`. Напиши тест на `pytest` с использованием `psycopg2`, который проверяет, что при добавлении второго студента в лист ожидания на один и тот же слот, его позиция (`position`) становится равна 2. Учти, что перед вставкой в `waitlist` нужно создать пользователей и слот.»

**Сгенерированный код (фрагмент):**
```python
cur.execute("INSERT INTO waitlist (slot_id, student_id, position, status) VALUES (200, 40, 1, 'waiting')")
cur.execute("INSERT INTO waitlist (slot_id, student_id, position, status) VALUES (200, 50, 2, 'waiting')")
```

**Проблема:**
При ручной верификации сгенерированного теста было выявлено, что ИИ **не учел реальную бизнес-логику проекта**.
В реальном файле `queries.sql` (запрос 4.1 «Добавить студента в лист ожидания») позиция в очереди должна вычисляться **автоматически базой данных** с помощью подзапроса `MAX(position) + 1`.
ИИ же просто «захардкодил» цифры `1` и `2` при вставке. Такой тест проверял бы только то, что PostgreSQL умеет вставлять числа, но **не тестировал бы реальный SQL-запрос из нашего проекта**.

**Исправление:**
Тест был переписан вручную. В него был вставлен оригинальный SQL-запрос из `queries.sql`:
```Python
cur.execute("""
            INSERT INTO waitlist (slot_id, student_id, position, status)
            VALUES (200, 50, (SELECT COALESCE(MAX(position), 0) + 1 FROM waitlist WHERE slot_id = 200), 'waiting')
            RETURNING position
        """)
```

**Вывод:** ИИ-ассистенты не знают контекста вашего проекта и вашей схемы БД. Они генерируют «средний» код по шаблону. Обязательна ручная проверка на соответствие архитектуре проекта.
