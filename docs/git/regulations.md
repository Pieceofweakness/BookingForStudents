# Общие принципы
1. Ветка `main` защищена. Прямые пуши в нее запрещены;
2. Одна задача = одна новая ветка = один pull request;
3. Все изменения проходят через ревью (минимум от 1);
4. Коммиты оформляются по стандарту Conventional Commits;
5. Все ключевые слова для закрытия задач пишутся в описании Pull Request.

# Правила оформления веток
Все ветки создаются от актуальной ветки `main`.

## Формат названия ветки
<тип>/<ID-задачи>-<краткое описание>

## Типы веток

| Тип                  | Назначение                               | Пример                  |
| -------------------- | ---------------------------------------- | ----------------------- |
| feature/id-описание  | Новая функциональность                   | feature/1-data-model    |
| docs/id-описание     | Документация                             | docs/5-update-readme    |
| fix/id-описание      | Исправление ошибок                       | fix/12-login-error      |
| chore/id-описание    | Инфраструктурные задачи                  | chore/4-gitignore-setup |
| test/id-описание     | Добавление/изменение тестов              | test/6-api-tests        |
| refactor/id-описание | Рефакторинг (без новой функциональности) | refactor/8-clean-models |
## Правила по оформлению названия
- Только латиница (английский язык);
- Только строчные буквы;
- Слова разделяются дефисом;
- Максимум 4-5 слов;
- Описывать суть, а не процесс.

## Примеры названий веток
### Правильные
feature/1-data-model
docs/5-update-readme
fix/15-waitlist-fifo
### Неправильные
feature/new_feature (нет ID, подчеркивание)
feature/2/update (лишние слеши)



# Правила оформления коммитов
Используется стандарт **Conventional Commits**. 

## Формат заголовка и описания коммита
<тип>(#<ID-задачи>): <краткое описание>

<тело коммита>
- Пункт 1
- Пункт 2

## Типы коммитов

| Тип      | Когда использовать                                     |
| -------- | ------------------------------------------------------ |
| feat     | Новая функциональность                                 |
| fix      | Исправление ошибок                                     |
| docs     | Изменения в документации                               |
| chore    | Рутина (обновление зависимостей, конфигов, .gitignore) |
| refactor | Рефакторинг без изменения поведения                    |
| test     | Добавление или изменение тестов                        |
| style    | Форматирование, пробелы (не меняет логику)             |
| perf     | Изменения, улучшающие производительность               |
| build    | Изменения, влияющие на сборку или внешние зависимости  |
| ci       | Изменения CI/CD                                        |

## Правила для заголовка коммита
- Длина до 72 символов;
- Строчная буква в начале описания;
- Без точки в конце;
- Обязательно указывать ID задачи.

## Правила для тела коммита (описания)
- Отделяется от заголовка пустой строкой;
- Объясняет зачем это сделано и детали реализации.

## Пример правильного коммита
fix(#15): prevent race condition on slot booking

При одновременной записи нескольких студентов на последнее место возникала ошибка: место записывалось за двумя людьми.

Добавлена блокировка строки слота через SELECT ... FOR UPDATE внутри транзакции. Теперь запросы на запись обрабатываются последовательно.



# Правила оформления Pull Request (PR)
PR - это оформленный результат работы. Ревьюер должен понять суть, не заглядывая в код

## Формат заголовка PR
<тип>(#<ID-задачи>): <краткое описание> (как у коммита)

<тело PR>

## Правила для заголовка PR
- Длина до 72 символов;
- Строчная буква в начале описания;
- Без точки в конце;
- Обязательно указывать ID задачи.

## Правила для тела PR (описания)
В описании обязательно должны быть разделы:
- Связанная задача: Closes #ID;
- Что сделано;
- Как проверить локально (инструкция);
- Риски / Затронутые модули.
