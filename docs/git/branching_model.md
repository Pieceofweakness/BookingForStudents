# Модель ветвления проекта

## Обоснование выбора
Для проекта выбрана модель **GitHub Flow** с единственной долгосрочной веткой main. Это обусловлено:
1. Полноценный Git Flow избыточен и усложняет процесс
2. Модель GitHub Flow предполагает, что main всегда готова к деплою
3. Низкий порог входа для участников 

## Структура веток 

| Ветка                | Назначение                                | Время жизни       |
| -------------------- | ----------------------------------------- | ----------------- |
| main                 | Стабильная версия, всегда готова к релизу | Постоянная        |
| feature/id-описание  | Новая функциональность                    | До слияния в main |
| docs/id-описание     | Документация                              | До слияния в main |
| fix/id-описание      | Исправление ошибок                        | До слияния в main |
| chore/id-описание    | Инфраструктурные задачи                   | До слияния в main |
| test/id-описание     | Добавление/изменение тестов               | До слияния в main |
| refactor/id-описание | Рефакторинг (без новой функциональности)  | До слияния в main |
## Правила именования веток
**Формат**: <тип>/<ID-задачи>-<краткое-описание>

Примеры:
- feature/1-data-model
- docs/5-update-readme

## Процесс работы
1. Задача добавляется в GitHub Issues
2. От main создается ветка с номером задачи
3. Разработка ведется в ветке
4. По завершении открывается Pull Request в main
5. Pull Request проходит ревью минимум от одного участника
6. После одобрения проходит слияние ветки в main
7. Ветка удаляется
