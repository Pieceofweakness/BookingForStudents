# ADR-001: Выбор архитектурного стиля

## Контекст

Разрабатывается система BookingForStudents — запись студентов на мероприятия и консультации преподавателей.

Функциональность (см. `docs/requirements/functional.md`):

- аутентификация с ролями (студент, преподаватель, администратор);
- создание слотов преподавателями (включая повторяющиеся);
- запись студентов с лимитом участников;
- лист ожидания при отсутствии мест;
- email-уведомления;
- форматы: офлайн, онлайн, гибрид.

Ключевые NFR (см. `docs/requirements/non_functional.md`):

- отклик API ≤ 500 мс при 100 одновременных пользователях;
- до 300 одновременных пользователей без деградации >30%;
- доступность ≥ 99% в учебный период;
- развёртывание одной командой через Docker;

Ограничения проекта:

- Команда: 4 человека.
- Срок: один семестр.
- Стек: Python, PostgreSQL, Docker.
- Приоритеты: скорость разработки, простота поддержки, низкий порог входа.

Требуется выбрать архитектурный стиль.

## Рассмотренные альтернативы

### 1. Монолит
Единое приложение: API, бизнес-логика и работа с БД в одном процессе. Просто, быстро, но границы модулей размываются со временем.

### 2. Микросервисы
Независимые сервисы со своими БД и API.
Гибко масштабируется, но требует Kubernetes, распределённых транзакций, мониторинга и зрелых CI/CD. Для команды из 4 человек и одного семестра — избыточно и противоречит требованию «развёртывание одной командой».

### 3. Модульный монолит
Монолит с чётким разделением на модули внутри (по DDD).
Даёт структуру микросервисов без их инфраструктурной сложности.
Позволяет позже выделить модуль в отдельный сервис без переписывания.

## Решение

Выбран модульный монолит на Python с разделением на модули:

- `auth` — аутентификация и сессии;
- `users` — профили пользователей;
- `slots` — слоты преподавателей;
- `bookings` — записи и лист ожидания;
- `notifications` — email-уведомления;
- `admin` — административные функции.

Правила изоляции:

- Модули общаются только через публичные интерфейсы (функции/классы).
- Каждый модуль владеет своим набором таблиц PostgreSQL. Прямой доступ
  к таблицам чужого модуля запрещён.
- Общая БД — одна, но с разделением по схемам (PostgreSQL schemas).

Развёртывание: Docker Compose — backend + PostgreSQL (+ Redis для
фоновых задач).

## Последствия

Положительные:

- Быстрый старт и низкий порог входа для команды без опыта Python.
- Простое развёртывание (`docker compose up`) — соответствует NFR.
- Единая транзакционная модель, нет распределённых транзакций.
- Тестирование проще: unit + integration в одном процессе.
- Возможность эволюции: при росте нагрузки модуль `notifications`
  или `bookings` можно выделить в отдельный сервис.
- Развивает ключевой навык: проектирование границ (bounded contexts),
  что востребовано на рынке.

Отрицательные:

- Горизонтальное масштабирование — только приложения целиком.
- Со временем возможен рост связности модулей без дисциплины.
- Общая БД усложнит будущее разделение, если не соблюдать изоляцию.
